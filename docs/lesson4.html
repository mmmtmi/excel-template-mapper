Lesson 4

Repository と DB を読む

この回は MySQL とのやり取りと、repository 層を置く意味を理解する回です。

この回のゴール

  • repository の役割を説明できる
  • Template と Rule の取得・保存 SQL を追える
  • service 層が repository interface を受ける理由を説明できる

読むファイル

  1. internal/store/mysql/template_repo.go
  2. internal/store/mysql/repos.go
  3. internal/store/mysql/mutations.go
  4. db/migrations/001_init.up.sql

見る順番

  1. migration でテーブル定義を確認する
  2. repository の read 系メソッドを見る
  3. mutation の write 系メソッドを見る
  4. resolver からどの関数が呼ばれているか戻って確認する

注目ポイント

  • mapping_templates と mapping_rules の主なカラム
  • GetTemplateByName が service にとってなぜ重要か
  • ListRulesByTemplateID が processor にどう使われるか
  • InsertTemplate / InsertRule の責務が resolver に漏れていないか

設計観点

このプロジェクトの service は具体的な MySQL 実装ではなく interface を受けます。これにより、将来は memory 実装や mock 実装へ差し替えられます。

service
  -> TemplateRepo interface
  -> RuleRepo interface

mysql package
  -> その interface を満たす具体実装

SQL で直接確認する

docker compose exec mysql mysql -uapp -papp excel_template_mapper -e "SELECT id,name,target,header_row,data_start_row FROM mapping_templates;"
docker compose exec mysql mysql -uapp -papp excel_template_mapper -e "SELECT id,template_id,source_type,source_key,target_label,required FROM mapping_rules;"

考える問い

  1. なぜ service が *sql.DB を直接持たず repository interface を受けているのか
  2. Rule が増えてきたとき、N+1 問題はどこで起きうるか
  3. Transaction が必要になる処理は今後どこに現れそうか
