Lesson 8

改善案を設計する

この回ではコードを読み終えた前提で、改善余地を整理し、最終的に .md へ落とし込める形まで具体化します。

この回のゴール

  • 現状実装の強みと弱みを整理できる
  • 改善候補を複数出せる
  • 改善案を .md 提案書の形にまとめられる

解説 1: 改善案の出し方

実務では「気になる点を挙げる」だけでは不十分です。改善対象、理由、効果、実装コストをセットで説明できる必要があります。

さらに GitHub でレビューしてもらう前提なら、第三者が読んで判断できる文書になっていることが重要です。

改善対象
  -> 現状の問題
  -> どう直すか
  -> 何が良くなるか
  -> どの程度の作業量か

読む 1: 改善候補を洗い出す

  • processor.go: transform の拡張性
  • reader.go: 複数表領域への弱さ
  • schema.resolvers.go: resolver の肥大化
  • schema.graphqls: JSON 文字列返却の扱い
  • internal/store/mysql: transaction 境界の不足

解説 2: 実装しやすい改善と難しい改善

  • 実装しやすい: transform の追加、GraphQL Query の追加、エラーメッセージ改善
  • 中規模: CELL type の追加、戻り値型の整理、テスト追加
  • 重い: 複数表領域対応、AI によるテンプレート推論、複雑な transform DSL

読む 2: 改善の優先順位を決める

候補を出したら、次は優先順位を付けます。判断軸を持たないと、思いつきの提案で終わります。

  • 学習効果が高いか
  • 既存設計への理解が深まるか
  • 実装規模が適切か
  • レビューしやすい差分になるか

読む 3: テスト観点を整理する

go test ./...
  1. internal/service/processor_test.go を読む
  2. 今あるテストで何が守られているかを書く
  3. まだ守られていない振る舞いを書く

提案書テンプレート（.md）

最終的には GitHub の PR に添付しやすいよう、Markdown でまとめます。

# 改善提案: タイトル

## 背景

## 現状の問題

## 提案内容

## 期待できる効果

## 影響範囲

## 実装方針

## テスト方針

## 優先度

提出物
